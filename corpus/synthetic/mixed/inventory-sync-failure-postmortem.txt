Incident Postmortem - Inventory Sync Failure. Incident ID POS-ERR-3102. Date 2026-05-02. Severity SEV-2.

Summary: The nightly batch job that syncs online-channel inventory counts against the in-store POS system failed silently for three consecutive nights (April 30, May 1, May 2) before being caught, due to a schema change in the POS export format that the sync job's parser did not reject outright but instead misread, producing counts that were consistently offset rather than obviously wrong. This is different from the loyalty double-credit incident (POS-ERR-3210) in one important way worth noting up front: that incident was caught within hours because the symptom (extra points) was immediately visible to customers, while this one went undetected for days precisely because a quietly wrong number looks the same as a correct number until someone checks it against reality.

Root cause: a POS software update on April 29 changed the export file's column order without changing the column headers, and the sync job's parser read columns by position rather than by header name. Every inventory count after the update was reading from the wrong column - in most cases this meant the sync job was writing a different SKU's count into a given item's record, rather than simply garbage or a null value, which is exactly why it wasn't caught by any existing validation - the numbers were plausible, just wrong, attached to the wrong SKU entirely.

Detection: a customer service escalation on May 2 reported that an item shown as in-stock online was unavailable in the store the customer visited to pick it up. This alone would likely have been treated as a one-off error, but a second nearly identical complaint arrived within the hour for a different item at a different store, which prompted an engineer to pull raw export files rather than trust the parsed sync output, at which point the column misalignment became visible immediately on inspection.

Impact: approximately 4,100 SKUs across all stores had incorrect online-availability counts for the three-day window. Online orders placed against an incorrectly-shown-available item that was actually out of stock defaulted to the standard oversell handling process, which is out of scope for this document but is referenced in the fulfillment team's own runbook, not reproduced here. No financial loss beyond the standard oversell handling cost was attributed directly to this incident; the primary cost was customer-facing - incorrect stock visibility for three days across a meaningful fraction of the online catalog.

Interaction with the corpus's other incidents: unlike the POS outage (POS-ERR-3021), which affected register connectivity broadly and was detected via direct monitoring, and the payment gateway failure (POS-ERR-3045), which was detected via transaction error rate, this incident is the only one of the four synthetic incidents in this corpus that was detected purely through downstream customer-facing symptoms rather than any internal monitoring signal - which is itself one of the corrective actions below, since it means the existing monitoring stack had a genuine blind spot for this failure class specifically, not just bad luck in this one instance.

Corrective actions: first, the sync job's parser was changed to read export columns by header name rather than positional index, which directly closes the specific failure mode that caused this incident. Second, a daily reconciliation check was added that samples a random 200 SKUs and compares the synced online count against a direct POS query, alerting on any mismatch above a small tolerance - this is meant to catch a similar but not identical future failure mode, since fixing the specific parser bug does not guarantee no other integration change could reintroduce a similar silent-corruption pattern somewhere else in the pipeline. Third, the POS vendor was asked to commit to a change-notification process for export format changes going forward, since the April 29 update that triggered this was not communicated to the integration team in advance, similar in spirit to the certificate rotation that triggered the payment gateway failure - both incidents trace back to an external system change made without notice to the teams depending on that system's stable interface.
